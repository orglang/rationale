# Что такое трансакция

> *"Видишь суслика? — Нет. — И я не вижу. А он есть!"*
> <p align="right">— ДМБ (2000)</p>

Попробуем разобраться, что такое трансакция, на примере из реальной жизни. Здесь важно не путать термин *трансакция* с привычным термином *транзакция* из других областей IT: в OrgLang он используется в особом значении.

## Зачем нужны трансакции

Представим интернет-магазин, который получил заказ. Чтобы отправить товар, магазину нужно подготовить отправление и передать его службе доставки.

Работу можно описать как последовательность процессов: один обрабатывает заказ, другой подготавливает отправление, третий участвует в передаче отправления перевозчику. Но такого описания недостаточно, чтобы гарантировать, что вся необходимая работа действительно может быть выполнена.

Что произойдёт, если у магазина нет собственной службы доставки? Как найти участника, способного предоставить нужную услугу? На каких условиях он согласится её предоставить? А если этот участник сам зависит от других участников?

Это вопросы не только о вычислениях и взаимодействии процессов. Они связаны с доступностью ресурсов и условиями, на которых одни участники системы предоставляют возможности другим.

**Трансакции в OrgLang рассматриваются как взаимодействия, связанные с согласованием условий предоставления ресурсов и организации работы между участниками системы.**

Чтобы понять, зачем нужен такой механизм, полезно разделить описание самой работы и организацию условий, при которых эта работа может быть выполнена.

## Процессы и взаимодействие

Процесс описывает работу и взаимодействие с другими процессами. Вызов процесса позволяет запросить выполнение работы, представленной определением целевого процесса. Сессионные типы предназначены для описания допустимого протокола взаимодействия сторон: какие действия и сообщения возможны и в каком порядке.

Вернёмся к интернет-магазину. Процесс обработки заказа может вызвать процесс подготовки отправления. Между воплощениями процессов может происходить взаимодействие по каналу, а допустимая последовательность действий может задаваться контрактом.

Такое описание отвечает на вопрос: **как должны взаимодействовать процессы, если необходимые участники и стороны взаимодействия доступны?**

Но оно само по себе не объясняет, как найти участника, способного предоставить нужную сторону взаимодействия, и как согласовать условия её предоставления. Для обсуждения этих вопросов необходимо рассмотреть отношения между участниками системы.

Здесь важно не смешивать три вещи:

- **Вызов процесса (`call`)** — запрос на выполнение работы, обозначенной целевым определением процесса.
- **Договорённость между участниками** — условия, на которых может быть предоставлена нужная возможность.
- **Создание воплощения процесса** — отдельное действие, связанное с обслуживанием вызова.

Эти вещи могут быть связаны, но не являются синонимами. В частности, сам вызов не означает, что провайдер уже найден, а наличие договорённости само по себе не означает, что новое воплощение процесса уже создано.

## От взаимодействия процессов к договорённостям

Предположим, что интернет-магазин не располагает собственной инфраструктурой доставки. Для обслуживания заказа ему нужен участник, который сможет предоставить соответствующую возможность.

Такой участник может быть доступен непосредственно или через отношения с другими участниками системы. Например, служба доставки может привлекать партнёров для отдельных этапов работы. Тогда для выполнения исходного запроса может потребоваться не только взаимодействие процессов, но и согласование условий между несколькими участниками.

В OrgLang для описания организации работы и отношений между участниками используется понятие **пула**. На этом уровне рассматривается, кто может предоставить нужную возможность и на каких условиях. Связанные с этим взаимодействия и согласование условий будем называть трансакционными.

Трансакционное взаимодействие не заменяет процесс и не является синонимом вызова процесса. Оно относится к другой задаче: согласованию условий, на которых участники могут предоставлять ресурсы и обеспечивать обслуживание запросов.

Таким образом, сценарий интернет-магазина помогает увидеть разницу между двумя вопросами:

1. Как должна выполняться работа и взаимодействовать процессы?
2. Как обеспечить, чтобы нужные участники и ресурсы были доступны на согласованных условиях?

Для дальнейшего обсуждения удобно различать **уровень процессов** и **уровень пулов**. На уровне процессов описываются процессы, их воплощения и взаимодействия, регулируемые сессионными типами. На уровне пулов рассматриваются взаимодействия пулов и договорённости между ними, для описания которых используются трансакционные типы. Это рабочие названия уровней; терминология и границы семантической модели ещё уточняются.

## Если у магазина нет собственной доставки

Вернёмся к заказу интернет-магазина. Процесс обработки заказа вызывает через `call` процесс подготовки отправления, обозначенный целевым именем `qn`. Но магазин не располагает собственной службой доставки. Кто в таком случае предоставит нужную возможность и как система найдёт подходящего участника?

Один из возможных вариантов — начать поиск с пула, который предоставляет процесс обработки заказа. Если он не может сам обеспечить нужную сторону взаимодействия, движок может проверить пулы, с которыми у него есть договорённости, а затем продолжить поиск через связанные с ними пулы. Например, партнёр магазина может работать со своей службой доставки или привлекать другого логистического оператора.

Если подходящий участник не найден, может потребоваться отдельная работа на уровне пулов: попытаться договориться с новым участником через структурный канал. Эту попытку, в свою очередь, может выполнять программа пула; если автоматического решения нет, может понадобиться человек, действующий от имени пула.

Это возможный сценарий, а не утверждённый алгоритм OrgLang. Он помогает сформулировать вопрос, который не решается одним описанием взаимодействия процессов: **как найти участника, который сможет обслужить вызов, и обеспечить условия для такого обслуживания?**

В этой картине важно различать три события:

- `call` запрашивает выполнение работы;
- договорённость задаёт условия, на которых участник может предоставить нужную возможность;
- создание воплощения целевого процесса происходит при обслуживании вызова и координируется движком.

Договорённость может существовать ещё до вызова; сама по себе она не означает, что воплощение процесса уже создано. И наоборот, вызов не гарантирует, что подходящий участник или договорённость уже найдены.

Пул-провайдер в этом примере отвечает за предоставляемую им сторону взаимодействия и её обслуживание в рамках применимого контракта. Структурный канал можно предварительно рассматривать как точку входа в протокол согласования условий, а не как одну конкретную договорённость. Точные отношения между структурным каналом, приватными каналами, трансакцией и договорённостью пока остаются открытым вопросом.

Детали поиска также ещё не определены: неизвестно, как выбирать между несколькими подходящими пулами и какие данные, помимо имени целевого процесса и каналов, связанных с `AssetVars`, должен передавать `call`.

## Объяснение формальное

За основу возьмем формальную модель теории сессионных типов [^1]. В рамках теории существует операция порождения нового процесса, которая является аналогом оператора `new` в языках программирования. В ванильной теории операция порождения является тривиальной, т.к. делается допущение о том, что все ресурсы доступны. Нам же придется копнуть чуть глубже и определить то, что происходит под капотом.

### Плейсхолдеры и идентификаторы

> [!WARNING]
> Вместо устоявшегося в промышленных языках программирования понятия *переменной* будем использовать термин *плейсхолдер*, т.к. он лучше передает семантику одноразовости подстановки.

Плейсхолдеры, которые мы будем записывать как *z*, *y*, *x* (латинские символы конца алфавита), являются частью синтакиса программ и обретают значение во время выполнения при подстановке. Ключевое отличие от функциональных ЯП, где на место плейсхолдера подставляется целое выражение, заключается в том, что мы вместо этого будем подставлять *идентификатор*. Идентификаторы, которые мы будем записывать как *a*, *b*, *c* (латинские символы начала алфавита), могут представлять разное в зависимости от интерпретации. Например, они могут представлять адреса в памяти, каналы коммуникации между процессами или, как в нашем случае, трансакции между пулами.

### Термы, значения и продолжения

Сопокупность термов пулов представляет состояние хозяйствующего субъекта, осуществляющего некоторую деятельность. Значения и продолжения пула представляют два разных вида информации. Значения - это небольшие (фиксированного размера) кусочки данных, тогда как продолжения - это данные, которые могут включать терм пула целиком.

Отличительная особенность заключается в том, что термы можно исполнять (execute), значения - разбирать (observe), а продолжения - применять (apply).

Формально пулы, значения и продолжения имеют грамматику, которая представлена в таблицах 1, 2 и 3.

| Значение *V*  | Семантика |
| :-----------  | :-------- |
| close          | Терминальный токен без какой-либо полезной информации. |
| grant(*c*) | Трансакция *c*, помеченная как grant. |
| revoke(*c*) | Трансакция *c*, помеченная как revoke. |
| choice(*c*) { *l* }   | Трансакция *c*, помеченная как choice, с классом *l*. |
| coop(*c*) { *w*·*q* } | Трансакция *c*, помеченная как coop, с долей *w* в производительности по именованному процессу *q*. |
| isol(*c*) { *w*·*q* } | Трансакция *c*, помеченная как isol, с долей *w* в производительности по именованному процессу *q*. |
| spawn(*c*)&nbsp;{&nbsp;*q*(&nbsp;*a*,&nbsp;*b*<sub>1</sub>,&nbsp;*b*<sub>2</sub>,...&nbsp;} | Трансакция *c*, помеченная как spawn, с вызовом именованного процесса *q* и аргументами *a*, *b*<sub>1</sub>, *b*<sub>2</sub>,... |

| Продолжение *K* | Семантика |
| :-------------- | :-------- |
| (close ⇒ *P*) | При получении терминального значения close продолжить как *P*. |
| (grant(*x*) ⇒ *P*) | При получении значения grant(*c*) продолжить как *P*[*c*/*x*]. Происходит связывание плейсхолдера *x* в рамках терма *P*. |
| (revoke(*x*) ⇒ *P*) | При получении значения revoke(*c*) продолжить как *P*[*c*/*x*]. Происходит связывание плейсхолдера *x* в рамках терма *P*. |
| (choice(*x*<sub>*𝚓*</sub>)&nbsp;{&nbsp;*𝚓*&nbsp;}&nbsp;⇒&nbsp;*P*<sub>*𝚓*</sub>)<sub>&nbsp;*𝚓*&nbsp;∈&nbsp;*𝙹*</sub> | При получении значения choice(*c*){*l*} для некоторого класса *l* ∈ *𝙹* продолжить как *P*<sub>*l*&nbsp;</sub>[*c*/*x*<sub>*𝚓*</sub>]. Происходит связывание плейсхолдера *x*<sub>*𝚓*</sub> в рамках терма *P*<sub>*𝚓*&nbsp;</sub> для каждого паттерна *𝚓* ∈ *𝙹*. |
| (coop(*x*) { *w*·*q* } ⇒ *P*) | При получении значения coop(*c*){*w*·*q*} продолжить как *P*[*c*/*x*]. Происходит связывание плейсхолдера *x* в рамках терма *P* и наращивание доли в производительности *q*. |
| (isol(*x*) { *w*·*q* } ⇒ *P*) | При получении значения isol(*c*){*w*·*q*} продолжить как *P*[*c*/*x*]. Происходит связывание плейсхолдера *x* в рамках терма *P* и сокращение доли в производительности *q*. |
| (spawn(*x*) { q } ⇒ *P*) | При получении значения spawn(*c*){*q*(*a*, *b*<sub>1</sub>, *b*<sub>2</sub>,...} для некоторого *q* ∈ *Q* продолжить как *P*[*c*/*x*]. Происходит связывание плейсхолдера *x* в рамках терма *P* и порождение процесса *q*. |
<p align="center"><sub>Таблица 2. Грамматика для продолжений</sub></p>

| Терм пула *P* | Семантика |
| :-------------- | :-------- |
| *c* ← *a* | Соединить каналы *a* и *c*. |
| *c*.*V* | Коммуницировать значение *V* в канал *c*. |
| case *c* *K* | Коммуницировать продолжение *K* в канал *c*. |
<p align="center"><sub>Таблица 3. Грамматика для термов</sub></p>

Где *x*, *x*<sub>*𝚓*</sub>, *z*, *y*<sub>1</sub>, *y*<sub>2</sub>,... представляют *плейсхолдеры*, тогда как *a*, *b*, *c*, *b*<sub>1</sub>, *b*<sub>2</sub>,... представляют *идентификаторы*.

Ключевой операцией языка является подача значения в продолжение, в результате которой образуется терм. Продолжение содержит терм пула (либо выбор между несколькими термами) со связанными плейсхолдерами в рамках него, и значение может как выбрать подходящий терм пула, так и предоставить идентификатор для подстановки.

Будем записывать данную операцию как *V* ▷ *K* и определим её следующим образом:  
> close⠀▷⠀(close ⇒ *P*)⠀≜⠀P  
> grant(*c*)⠀▷⠀(grant(*x*) ⇒ *P*)⠀≜⠀*P*[*c*/*x*]  
> revoke(*c*)⠀▷⠀(revoke(*x*) ⇒ *P*)⠀≜⠀*P*[*c*/*x*]  
> choice(*c*) { *l* }⠀▷⠀(choice(*x*<sub>*𝚓*</sub>) { *𝚓* } ⇒ *P*<sub>*𝚓*</sub>)<sub>&nbsp;*𝚓* ∈ *𝙹*</sub>⠀≜⠀*P*<sub>*l*&nbsp;</sub>[*c*/*x*<sub>*j*</sub>]  
> coop(*c*) { *w*·*q* }⠀▷⠀(coop(*x*) { *w*·*q* } ⇒ *P*)⠀≜⠀*P*[*c*/*x*]  
> isol(*c*) { *w*·*q* }⠀▷⠀(isol(*x*) { *w*·*q* } ⇒ *P*)⠀≜⠀*P*[*c*/*x*]  
> spawn(*c*) { *q*(*a*, *b*<sub>1</sub>, *b*<sub>2</sub>,...) }⠀▷⠀(spawn(*x*) { *q* } ⇒ *P*)⠀≜⠀*P*[*c*/*x*]   

Для остальных комбинаций *V* и *K* операция *V* ▷ *K* остается неопределенной.

### Типы, ограничения, уточнения

Выражения типов соединяются при помощи *связующих*, которые могут быть унарными (например, up `￪`), бинарными (например, lolli `⊸`) или n-арными (например, external choice `&{...}`). Cлева от связующего в квадратных скобках может быть определено *ограничение*, а справа - *уточнение*.

Мы интерпретируем идентификаторы как приватные трансакции между пулами, в рамках которых осуществляется обмен сообщениями. Пул 1 может опубликовать значение и/или подписать продолжение в рамках трансакции, так что данные сообщения будут получены пулом 2 на другом конце трансакции. Значение *V* может быть опубликовано в трансакцию *a* при помощи конструкции *a*.*V*. Данное сообщение затем будет получено подпиской case *a* *K*, которая подаст полученное значение *V* в продолжение *K* для определения дальнейшего развития событий.

> *y*<sub>1</sub> : *B*<sub>1</sub>,...,*y*<sub>*n*</sub> : *B*<sub>*n*</sub> ⊢ *P* :: (*z* : *A*)

Пул *P* может *использовать* трансакции *y*<sub>1</sub>,...,*y*<sub>*n*</sub> для коммуникации с другими пулами согласно типам *B*<sub>1</sub>,...,*B*<sub>*n*</sub> соответственно и *предоставляет* трансакцию *z* типа *A*, в рамках которой с ним могут коммуницировать другие.

| Тип трансакции T | Семантика |
| :--------------- | :-------- |
| 𝟏  | Отправить токен close без продолжения. |
| ￪ *A* | Отправить токен grant. Продолжить как *A*. |
| ￬ *A* | Принять токен revoke. Продолжить как *A*. |
| [*l* ∈ *L*] ⨁{ *l* : *A*<sub>*l*</sub> } | Отправить токен choice с классом *l* ∈ *L*. Продолжить как *A*<sub>*l*</sub>. |
| [*l* ∈ *L*] &{ *l* : *A*<sub>*l*</sub> } | Принять токен choice с классом *l* ∈ *L*. Сопоставить класс с паттерном и продолжить как *A*<sub>*l*</sub>. |
| [*w*·*q* ∉ *Q*] ⇱ [*Q*'] *A* | Отправить токен coop с именем процесса *q* и долей в производительности *w* такими, что *w*·*q* ∉ *Q*. Вычислить объединение *Q*' = *Q* ⋃ {*w*·*q*}. Продолжить как [*Q*'] *A*. |
| [*w*·*q* ∈ *Q*] ⇲ [*Q*'] *A* | Принять токен isol с именем процесса *q* и долей в производительности *w* такими, что *w*·*q* ∈ *Q*. Вычислить пересечение *Q*' = *Q* ⋂ {*w*·*q*}. Продолжить как [*Q*'] *A*. |
| *q*(*a*,&nbsp;*b*<sub>1</sub>,&nbsp;*b*<sub>2</sub>,...)&nbsp;[*q*&nbsp;∈&nbsp;*Q*]&nbsp;⊸&nbsp;[*Q*]&nbsp;*A*<sub> | Принять токен spawn с именем процесса *q* и каналами процессов *a*, *b*<sub>1</sub>, *b*<sub>2</sub>,... Породить процесс *q*. Продолжить как [*Q*] *A*. |
<p align="center"><sub>Таблица 4. Грамматика для типов</sub></p>

Где *Q* представляет мультимножество имен процессов, кратность *w* в котором представляет долю в производительности { *w*<sub>1</sub>·*q*<sub>1</sub>, *w*<sub>2</sub>·*q*<sub>2</sub>,... }.

### Примеры

```
t0 = &{  
    new : q(a, b1, b2,...) [q ∈ Q] ⊸ [Q] t0,  
    end : [Q = {}] ￬ 𝟏,  
    more : t1,  
    less : t2  
}  

t1 = ￪ ([w·q ∉ Q] ⇱ [Q ⋃ {w·q}] t0)

t2 = ￪ ([w·q ∈ Q] ⇲ [Q ⋂ {w·q}] t0)
```

Где исходно *Q* = {}.

[^1]: Luis Caires and Frank Pfenning. 2010. Session Types as Intuitionistic Linear Propositions.
